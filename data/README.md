## Dataset overview

The dataset consists of **9 relational tables** totaling approximately 100,000 orders.

| File | Rows (approx.) | Description |
|------|---------------:|-------------|
| `olist_customers_dataset.csv` | 99,441 | Customer identifiers and location |
| `olist_geolocation_dataset.csv` | 1,000,163 | Brazilian zip code coordinates (lat/lng) |
| `olist_order_items_dataset.csv` | 112,650 | Line items per order — products, prices, freight |
| `olist_order_payments_dataset.csv` | 103,886 | Payment method, installments, amount |
| `olist_order_reviews_dataset.csv` | 99,224 | Customer satisfaction reviews and scores |
| `olist_orders_dataset.csv` | 99,441 | Order status and timestamps |
| `olist_products_dataset.csv` | 32,951 | Product attributes and dimensions |
| `olist_sellers_dataset.csv` | 3,095 | Seller identifiers and location |
| `product_category_name_translation.csv` | 71 | Portuguese → English category names |

**Total dataset size:** ~120 MB uncompressed across all CSVs.

### Relational model (conceptual)

```
                customers
                    │
                    │ customer_id
                    ▼
      ┌─────────────────────────┐
      │        orders           │◄────────────── order_reviews
      │  (order_id = PK)        │◄────────────── order_payments
      └───────────┬─────────────┘
                  │ order_id
                  ▼
           order_items
                  │
        ┌─────────┼──────────┐
        │         │          │
        ▼         ▼          ▼
   products    sellers    (shipping_limit_date, price, freight)
        │
        ▼
  category_translation

  (geolocation is standalone: zip code → lat/lng lookup)
```

The `order_items` table is the bridge between orders, products, and sellers. Every revenue or product-level analysis joins through it.

Customer records. **Note the two customer identifiers** — see [Critical schema notes](#critical-schema-notes).

| Column | Type | Notes |
|--------|------|-------|
| `customer_id` | string | Per-order identifier — **NOT unique per customer** |
| `customer_unique_id` | string | True customer identity — use this for customer counts |
| `customer_zip_code_prefix` | int | First 5 digits of Brazilian zip code |
| `customer_city` | string | City name |
| `customer_state` | string (2) | Brazilian state abbreviation (SP, RJ, MG, …) |

| Column | Type | Notes |

| `geolocation_state` | string (2) | State abbreviation |

## Critical schema notes

### 1. `customer_id` vs `customer_unique_id`

**This is the single most common mistake analysts make with this dataset.**

- `customer_id` is generated **per order**. If the same person places three orders, they get three different `customer_id` values.
- `customer_unique_id` is the **true customer identity** that persists across orders.

**Correct usage:**

```sql
-- CORRECT: counts unique customers
SELECT COUNT(DISTINCT customer_unique_id) FROM customers;
-- Returns ~96,096

-- WRONG: counts order-scoped customer records, inflating the number
SELECT COUNT(DISTINCT customer_id) FROM customers;
-- Returns ~99,441 — overcounts
```

In the ETL, `customer_id` is preserved for joining, but **all customer-level analysis uses `customer_unique_id`**.

### 2. `order_status` filtering

For revenue, delivery, and satisfaction analysis, filter to `order_status = 'delivered'`. Other statuses introduce noise:

- `canceled` and `unavailable` have no delivery
- `shipped`, `invoiced`, `processing`, `approved`, `created` are in-flight
- Only `delivered` represents a completed transaction

**Correct usage:**

```sql
SELECT SUM(price + freight_value)
FROM order_items oi
JOIN orders o ON oi.order_id = o.order_id
WHERE o.order_status = 'delivered';
```

### 3. `order_items` grain

`order_items` is at the **line item** level, not the order level. One order can have multiple rows. When you want order-level metrics:

```sql
-- Correct: order-level aggregation
SELECT
    order_id,
    SUM(price)         AS order_price,
    SUM(freight_value) AS order_freight,
    COUNT(*)           AS n_items
FROM order_items
GROUP BY order_id;
```

Forgetting this inflates counts and averages.

### 4. Payment and review multiplicity

Both `order_payments` and `order_reviews` can have **multiple rows per order**.

- Payments: an order may be split across methods or installments.
- Reviews: the source has known duplicates that the ETL deduplicates on load, keeping the latest by `review_answer_timestamp`.

Always aggregate to the order level before joining to `orders`.

## Data quality issues

The dataset is clean overall, but a few quirks require handling. Each is addressed in `src/etl.py` and documented here so reviewers understand the mitigations.

| Issue | Impact | Mitigation in this project |
|-------|--------|----------------------------|
| **Missing delivery timestamps** for undelivered orders | `order_delivered_customer_date` is NULL for canceled/pending orders | Filter to `order_status = 'delivered'` in analysis |
| **Null product categories** | ~1.8% of products have no category | `COALESCE` with Portuguese name fallback in category joins |
| **Missing product dimensions** | ~0.6% of products lack weight/dimensions | Exclude from freight-per-kg analysis |
| **Integer columns stored as floats** | `product_name_lenght` = `"40.0"` fails PostgreSQL `COPY` | Cast via `INTEGER_COLUMNS` map in `src/config.py` |
| **Duplicate `review_id` values** | Review counts inflate if not deduped | Dedupe in `src/etl.py` `transform()`, keep latest by `review_answer_timestamp` |
| **Orphan records** | Some reviews reference order IDs not present in `orders` | No FK constraints; `LEFT JOIN` in queries |
| **Zip code prefix collisions** | `geolocation` has many rows per zip prefix | Aggregate to mean lat/lng when using for joins |
| **Geographic concentration** | SP dominates; sparse data for some northern states | Segment-level analysis only for high-volume states |

### Known source-data quirks

**Misspelled column names.** The `products` CSV spells columns as `product_name_lenght` and `product_description_lenght` — with `lenght` instead of `length`. This project preserves the misspelling in the schema and ETL so that joins and downstream code match the source byte-for-byte. Correcting it would silently break compatibility with the original CSV.

**Float-stored integers.** Several product columns that represent integers (`product_name_lenght`, `product_description_lenght`, `product_weight_g`, etc.) are stored as floats in the source (`40.0`, `500.0`). The ETL casts them to pandas `Int64` (nullable integer) so the PostgreSQL `COPY` command receives clean integers.

**Date strings with mixed formats.** A few timestamps in the source appear as `"YYYY-MM-DD HH:MM:SS"` and others as `"YYYY-MM-DD"`. The ETL parses all datetime columns with `errors="coerce"`, converting unparseable values to `NaT` rather than crashing the pipeline.

**Null markers in the CSV.** Some text fields contain the literal strings `"nan"`, `"None"`, or empty whitespace. The ETL normalizes these to proper SQL `NULL` values.

## How to download and place the files

### Step 1 — Download from Kaggle

1. Sign in to Kaggle (free account): <https://www.kaggle.com>
2. Go to the dataset: <https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce>
3. Click the **Download** button (~45 MB ZIP)
4. Accept the dataset's terms

### Step 2 — Extract into `data/raw/`

Unzip the archive and move the 9 CSV files into `data/raw/`. The final structure must match:

```
data/raw/
├── olist_customers_dataset.csv
├── olist_geolocation_dataset.csv
├── olist_order_items_dataset.csv
├── olist_order_payments_dataset.csv
├── olist_order_reviews_dataset.csv
├── olist_orders_dataset.csv
├── olist_products_dataset.csv
├── olist_sellers_dataset.csv
└── product_category_name_translation.csv
```

### Step 3 — Verify

From the project root:

```bash
# macOS / Linux
ls -1 data/raw/*.csv | wc -l
# Expected output: 9

# Windows PowerShell
(Get-ChildItem data/raw/*.csv).Count
# Expected output: 9
```

### Step 4 — Run the pipeline

```bash
python scripts/run_pipeline.py
```

The ETL reads all 9 files, cleans them, and loads them into PostgreSQL. Cleaned Parquet copies land in `data/processed/`.

## How the pipeline consumes this data

The flow, in order:

1. **`src/etl.py::extract()`** reads each CSV in `data/raw/` into a pandas DataFrame using the `CSV_FILES` mapping in `src/config.py`.
2. **`src/etl.py::transform()`** applies cleaning:
   - Datetime parsing for known timestamp columns (`DATE_COLUMNS` in `config.py`)
   - Integer casting for known integer columns (`INTEGER_COLUMNS` in `config.py`)
   - String trimming and null normalization
   - `review_id` deduplication
3. **`src/etl.py::load()`** writes the cleaned DataFrames into PostgreSQL via `COPY` (with `to_sql` as a fallback).
4. **`transform()` also writes Parquet copies** to `data/processed/`. These are the source of truth for feature engineering — reading Parquet is faster than re-reading CSVs.
5. **`src/features.py`** reads from `data/processed/` and writes `features_*.parquet`, also in `data/processed/`.
6. **Notebooks** read from either the PostgreSQL database (via `src/db_utils.py`) or the Parquet files (for feature tables), depending on which is more appropriate.

**Why Parquet for intermediate artifacts:**

- **Columnar** — reads only the columns you need.
- **Preserves types** — no re-parsing datetimes or re-casting integers.
- **Compressed** — 5–10× smaller than CSV.
- **Fast** — reads in milliseconds vs seconds for CSV.

The CSV files in `data/raw/` are only read once, at ETL time. Everything downstream uses Parquet or the database.
